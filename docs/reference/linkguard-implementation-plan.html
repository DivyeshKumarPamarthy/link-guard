LinkGuard: Implementation Plan

A four-phase plan with 26 modules. Phase 1 (engine core and web app) is the part delivered this semester. Every module lists what to build, design notes, a "done when" checklist and the edge cases to expect.

313 edge cases are written as situation then what should happen then the reason code the engine emits. Treat each row as a test case. Tick the "done when" boxes as you go: they are saved in your browser.

Ground rules that apply to every phase

Verdict vocabulary

  • status: completed, rejected (unsafe target) or unsupported (link type not handled)
  • verdict (only when completed): SAFE, SUSPICIOUS, UNSAFE, UNABLE_TO_VERIFY
  • confidence: high, medium or low; scope: full, partial or metadata-only
  • Reason codes are stable UPPER_SNAKE identifiers with a prefix

Honesty rules

  • No signal is not proof of safety: a clean partial scan says "No issues found in the checked part"
  • Missing evidence never becomes evidence of safety; failures are Unable to Verify
  • Positive evidence of risk beats missing evidence
  • Reputation and other signals never lower risk found by the engine's own checks
  • Every report states what was actually read

Safety rules

  • Downloaded files are never executed
  • Every piece of remote data (URLs, filenames, headers, torrent names) is hostile: escape on display, sanitize in logs, never use as a path
  • Only the safe fetcher contacts user-supplied URLs, and the SSRF checks run on every request and every redirect hop
  • Secrets come from the environment, never from code or the extension

M1Setup and API contract

Create the skeleton everything else plugs into and freeze the contract between backend and web app so the two can be built in parallel.

What we build

  • Repo layout: backend/, web/, extension/ (empty until Phase 2), samples/, docs/; README with one-command setup
  • FastAPI app with POST /api/scans (submit a link), GET /api/scans/{id} and GET /api/scans (recent scans)

  • Reason codes are UPPER_SNAKE with a prefix: URL_, FETCH_, TYPE_, EXT_, REDIR_, LINK_, SCAN_; later PE_, ARCH_, DOC_, SCRIPT_, TOR_, REP_, ANALYSIS_

M2SSRF-safe fetcher

The single, hardened component that is allowed to contact user-supplied URLs. It validates the target, follows redirects safely, and reads only as much of the file as needed.

What we build

  • URL validation: scheme (http/https only), host present, no userinfo (user:pass@), port in the allow-list, length limit
  • Normalize the host (lowercase, IDNA/punycode, strip trailing dot) and keep both the display form and the punycode form
  • Resolve DNS (A and AAAA), classify every returned address, reject the scan if any address is not public
  • Connect to the validated IP (pinned) while sending the original Host header and SNI, so a second DNS lookup cannot swap the target
  • Follow redirects manually: max 5 hops, re-run every check on every hop, record each hop (URL, status, IP class)
  • Probe with HEAD, fall back to GET with Range: bytes=0-(N-1); always send Accept-Encoding: identity
  • Stream the body with a hard byte cap and a total deadline; stop and mark scope partial when the cap is hit
  • Return a FetchResult: bytes, total size if known, whether Range worked, whitelisted response headers, hop list, timings
  • Never forward cookies or credentials; fixed, honest User-Agent; trust_env=False so proxy variables cannot bypass the checks

Design notes

  • Libraries: httpx (custom transport or the sni_hostname request extension for pinned connects), ipaddress, idna, socket.getaddrinfo run in a thread
  • Blocked address space: loopback, private (RFC 1918), link-local including the cloud metadata address 169.254.169.254, CGNAT 100.64.0.0/10, multicast, reserved, unspecified 0.0.0.0, IPv6 loopback/ULA/link-local, and IPv4-mapped IPv6 forms of any of those. Use ipaddress properties (is_global) rather than a hand-written list
  • Starter defaults (all configurable): head fetch 5 MB, full-download cap 50 MB (used from Phase 2), connect timeout 5 s, total deadline 20 s, 5 redirects
  • Nothing else in the codebase may open an outbound connection to a user-supplied URL. This module is the choke point

M3Link router

Decide what kind of link was pasted, resolve redirect chains, and send the link to the right handler. In Phase 1 only HTTP/HTTPS is handled; everything else gets a clear message.

What we build

  • Input cleaning: trim whitespace, strip surrounding quotes/angle brackets/trailing punctuation, add https:// when the scheme is missing, reject several URLs in one box
  • Classify: http(s) goes to the fetcher; magnet:, ftp: and URLs ending in .torrent are unsupported (named, with "planned for Phase 3" where relevant); anything else is rejected
  • Label a link shortened when it redirects at least once to a different host; the redirect logic itself lives in the fetcher
  • Detect "this is a web page, not a file": text/html or application/xhtml+xml with no Content-Disposition: attachment
  • Detect likely cloud-share pages (Drive, Dropbox, OneDrive, Mega) and show a hint about direct-download links
  • Build the redirect-chain view model for the report (each hop: URL, status, address class)

Design notes

  • Do not depend on a list of known shorteners. Any redirect is handled the same way; a list may only improve labels
  • Keep classify(url) a pure function so it is trivial to unit-test
  • Torrent and magnet handlers are stubs returning unsupported until Phase 3, but their interface is defined now

M4File-type detection and mismatch

Work out what the file really is from its bytes, compare that with everything else that claims to describe it (filename, Content-Type), and turn disagreements into reasons. This is the headline check: a file named movie.mp4 that is really an .exe.

What we build

  • Signature table for the 16 supported formats with offset, bytes and the family each belongs to (executable, archive, document, script, media, image)
  • detect_type(bytes) returning type, family and confidence (certain / probable / unconfirmed)
  • Extract the claimed name: Content-Disposition filename, then final URL path, then original URL path; normalize (decode, strip path, strip trailing dots/spaces, lowercase)
  • Extension analysis: last extension, the full extension chain (double extensions), and a risky-extension list (.scr, .lnk, .hta, .vbs, .cmd, .jar, .com, .pif) even though they are outside the 16 formats
  • Compare real type, claimed extension and Content-Type using equivalence classes (for example .mp4 is close to .m4a/.mov; .docx belongs to the ZIP family)
  • Emit reasons with severity (weights live in M5); keep each check a small, separate, testable function
  • Secondary opinion from python-magic/libmagic for logging only. The project's own table is authoritative

Design notes

  • Executable family covers PE (MZ with PE\0\0 at e_lfanew), ELF (\x7fELF) and Mach-O. An executable posing as media is a finding regardless of platform
  • ZIP-based formats (.docx, .xlsx, also .jar and .apk) all start with PK\x03\x04. The subtype comes from entry names ([Content_Types].xml plus word/ or xl/) which usually sit near the start. If the head does not show them, report "ZIP-based, subtype unconfirmed"; Phase 3 resolves it with a tail range
  • .msi shares the OLE signature D0CF11E0A1B11AE1 with legacy .doc/.xls. Phase 1 reports "OLE container" and treats .msi as consistent
  • Text formats (.js, .ps1, .bat) have no magic bytes: detect "text" (check BOMs for UTF-8/UTF-16), then rely on extension and light content hints
  • Reminders: PNG 89 50 4E 47 0D 0A 1A 0A; JPEG FF D8 FF; PDF %PDF- (may start within the first 1024 bytes); MP4 ftyp at offset 4; MP3 ID3 or frame sync FF Ex/Fx; 7z 37 7A BC AF 27 1C; RAR4 Rar!\x1A\x07\x00; RAR5 Rar!\x1A\x07\x01\x00

M5Scoring and explanation engine v1

Turn the list of findings into a verdict people can trust, with confidence, scope and a readable explanation. The extension popup will later reuse the same headline.

What we build

  • Reason model: code, severity, weight, message, evidence (small dict), group
  • Weight table in config, not code, with a starter set (see notes)
  • Aggregation: within each group only the highest weight counts (avoids double-counting correlated signals); sum across groups; cap at 100
  • Hard rules: certain reasons set a minimum verdict regardless of score (executable disguised as media is at least Unsafe)
  • Verdict mapping from thresholds; handling of rejected/unsupported statuses and Unable to Verify cases
  • Confidence from scope (full / partial / metadata-only), Range support and which signals were available
  • Explanation builder: reasons ordered by weight then code, plus a one-line headline ("Blocked: file named .mp4 is actually a Windows executable")
  • Scope label in the output ("first 5 MB checked of 1.2 GB")
  • Golden-file tests: input fixtures produce expected JSON output

Design notes

  • Starter thresholds (tuned in Phase 4): 0-29 Safe, 30-59 Suspicious, 60-100 Unsafe
  • Starter weights: TYPE_MISMATCH_EXEC 70 (hard rule: Unsafe); EXT_DOUBLE 40; TYPE_MISMATCH_TEXT 20; TYPE_MISMATCH_OTHER 15; EXT_RISKY 15; REDIR_DOWNGRADE 10; REDIR_LONG_CHAIN 10; CONTENT_TYPE_MISMATCH 10; REDIR_CROSS_DOMAIN 5; informational reasons weigh 0

M9Isolated worker

Run fetching and analysis in a throw-away container so a hostile file or a parser bug cannot touch the API, the database or the network behind it.

What we build

  • Worker image: minimal Python base, non-root user, only the analysis code and pinned dependencies
  • Job runner starts one container per scan with --read-only, --tmpfs /tmp:size=64m,noexec,nosuid, --cap-drop ALL, --security-opt no-new-privileges, --pids-limit, memory and CPU limits, no mounted volumes, no Docker socket
  • Network policy: outbound internet only; private ranges, the cloud-metadata address and the host/bridge gateway are blocked
  • Communication: job input as JSON on stdin or environment; output as a single size-limited JSON document on stdout
  • The API validates worker output against the schema and treats it as untrusted
  • Lifecycle: timeout, kill and remove the container always; a reaper cleans orphaned containers at startup and periodically
  • Concurrency limit and a queue with backpressure
  • Development fallback: run the worker as a subprocess, loudly labeled "NOT ISOLATED" in logs, for machines without Docker

Design notes

  • The M2 fetcher runs inside the worker. Keep the code-level SSRF checks as well: network rules and code checks are two independent layers
  • Prefer a small job-runner component with Docker access over mounting /var/run/docker.sock into the API (socket access is effectively root on the host)
  • Container start costs around a second. Per-scan fresh containers are the strongest; pre-warmed single-use containers are faster. Never reuse a container for two scans
  • Stretch hardening: rootless Docker, gVisor/Kata, a custom seccomp profile

Test strategy

Unit tests

  • Table-driven tests for URL parsing, IP classification, router, signatures and scoring
  • Golden JSON outputs for the scorer
  • Every reason code has at least one test that produces it

Integration and end-to-end

  • Everything runs against the local demo server, never the real internet
  • Each acceptance-matrix row is an automated test
  • Extension flows are tested manually with a written checklist per phase (and the service worker deliberately stopped)

Security, manual and demo

  • SSRF table and fuzzing of parsers inside the worker
  • Provider mocks plus a short manual live smoke test before each demo
  • A full demo rehearsal with the network off, and a backup video

CI from week 1: run unit tests, contract tests and the acceptance matrix on every push. A failing matrix row blocks the merge. This is what makes it safe to change weights and rules in later phases.

Glossary

TermMeaning
SSRFServer-Side Request Forgery: tricking our server into requesting an internal or sensitive address.

Range requestAn HTTP request for only part of a file (Range: bytes=0-999). A supporting server answers 206 Partial Content.
Magic bytesThe first bytes of a file that identify its real format regardless of the name.
EntropyA measure of randomness in bytes (0 to 8). Packed, encrypted or compressed data scores high.
PEPortable Executable, the file format of Windows .exe, .dll and .sys files.
YARAA pattern-matching language for describing and detecting file characteristics.
OLE / CFBAn older compound container format used by legacy Office files and .msi installers.
Zip bombA small archive crafted to expand to an enormous size when extracted.
PolyglotA file that is valid in two formats at once, used to slip past type checks.
CloakingA server showing harmless content to scanners and something else to real users.
